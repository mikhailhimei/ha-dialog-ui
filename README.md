# HA Dialog UI для Home Assistant

Интеграция добавляет панель «Диалог» для настройки голосовых команд, запуска
скриптов Home Assistant, управления таймерами и будильниками. В Assist выберите
диалоговую систему HA Dialog UI; распознавание речи и TTS настраиваются
в самом Home Assistant.

## Установка и обновление

Репозиторий: https://github.com/mikhailhimei/ha-dialog-ui. Для HACS добавьте его
как пользовательский репозиторий категории «Интеграция».

1. Скопируйте `custom_components/ha_dialog_ui` в `config/custom_components/` Home Assistant.
2. Перезапустите Home Assistant.
3. Откройте «Настройки → Устройства и службы → Добавить интеграцию → HA Dialog UI».
4. Откройте панель «Диалог» из бокового меню.

При обновлении заменяйте всю папку интеграции, включая `static`, и перезапускайте
Home Assistant. Если интерфейс остался прежним, обновите страницу с очисткой кеша.

## Как настроить команду

1. В «Основных командах» создайте команду и задайте название.
2. Укажите фразы для запуска. Варианты разделяйте `;`: `включи свет; зажги свет`.
   Окончания можно записать как `кухн(я|ю|е)`. Знак `?` делает группу необязательной:
   `зал(а|е)?` распознаёт также слово «зал».
3. Выберите источник ответа: из списка фраз или из скрипта.
4. При необходимости выберите скрипт Home Assistant.
5. Добавьте текст ответа. Через «Настроить логику» подключите прямые команды
   для распознавания переменных и продолжения диалога.

Прямая команда распознаёт значение во фразе: например, `${room}` в «Включи свет
в ${room}». Вложенные команды позволяют переиспользовать наборы значений.
Продолжения задают следующий шаг диалога. При отсутствии подходящего продолжения
диалог завершается. Переход по типу результата скрипта имеет приоритет над обычным.

Скрипт выполняется для ответа из скрипта, распознанной прямой команды или
финального ответа без обычного продолжения. При ответе из списка с обычным
продолжением скрипт на этом шаге не запускается.

## Ответы и переменные

В текстах ответов команд используются подстановки `${имя}`. Например:

```text
Температура в комнате — ${temperature} градусов.
```

Для ответа из списка интеграция может использовать распознанные значения
команды. Для ответа из скрипта данные передаются через `variables` действия
`ha_dialog_ui.send_command`. Имя в `${temperature}` должно совпадать
с ключом `temperature` в объекте переменных. Регистр имени имеет значение.

Если переменная не передана, её подстановка в ответе команды станет пустой
строкой. Проверьте названия переменных перед использованием команды.

Текст ответа — это шаблон интеграции, а не Jinja-шаблон Home Assistant:
`${temperature}` применяется в редакторе команды, а `{{ ... }}` — внутри YAML-скрипта.

### Пример: ответ из скрипта

В редакторе команды:

1. Выберите источник «Ответ из скрипта» и свой скрипт Home Assistant.
2. В списке ответов выберите «По типу результата скрипта».
3. Укажите тип результата `success`.
4. Задайте текст: `Температура в комнате — ${temperature} градусов.`

В HA создайте скрипт:

```yaml
alias: Ответить о температуре
sequence:
  - action: ha_dialog_ui.send_command
    data:
      clientId: "{{ dialog_payload.client_id }}"
      deviceId: "{{ dialog_payload.device_id }}"
      actionType: success
      variables:
        temperature: "{{ states('sensor.room_temperature') }}"
```

Замените `sensor.room_temperature` на свою сущность. Интеграция ожидает результат
скрипта до 8 секунд. Действие `send_command` отправляет событие ответа; обычного
`return` из HA-скрипта недостаточно. Скрипт должен отправить результат, пока
интеграция ещё ожидает ответ.

Если скрипт передаёт другой тип, выбирается ответ с соответствующим типом.
Если тип не указан в событии, механизм ответов команд использует основной ответ
или ответ для продолжения. У действия `send_command` поле типа обязательно.

## Если команда не распознана

В «Ответах по умолчанию» откройте настройку «Если ничего не нашёл» (`default_main`).

1. Включите «Передать команду серверу».
2. Выберите скрипт Home Assistant. Вариант «Использовать существующие сценарии»
   сохраняет прежнюю маршрутизацию через привязки сценариев.
3. Тип результата здесь фиксирован: `success`.
4. В поле «Текст озвучки» укажите `${reply}` или, например, `Ответ: ${reply}`.

Пример скрипта:

```yaml
alias: Ответ на нераспознанную фразу
sequence:
  - variables:
      reply: "Вы сказали: {{ dialog_payload.text }}"
  - action: ha_dialog_ui.send_command
    data:
      clientId: "{{ dialog_payload.client_id }}"
      deviceId: "{{ dialog_payload.device_id }}"
      actionType: success
      variables:
        reply: "{{ reply }}"
```

Здесь `reply` может содержать результат ваших действий или обращения к другому
сервису. Интеграция подставит его в текст озвучки и передаст результат в Assist.
Голос и синтез речи определяются TTS выбранного Assist-пайплайна; отдельный вызов
TTS из скрипта не требуется.

Если результат не пришёл вовремя, имеет неподходящий тип или не даёт текста,
используется обычное ответное сообщение настройки. Оно сохраняется отдельно
и снова отображается при выключении передачи. Переключатель «Завершать диалог»
определяет завершение диалога для этой настройки.

## Поля `ha_dialog_ui.send_command`

| Поле | Что передать |
| --- | --- |
| `clientId` | `{{ dialog_payload.client_id }}` — ID клиента из исходного запроса. |
| `deviceId` | `{{ dialog_payload.device_id }}` — ID устройства из того же запроса, без изменений. |
| `actionType` | Тип результата: например, `success`. Должен соответствовать настроенному ответу. Это не UUID команды. |
| `variables` | Объект с данными: `{reply: "Готово", temperature: 22}`. Для подстановки используйте `${reply}` и `${temperature}`. Допускается также JSON-объект строкой. |
| `useDeclension` | Подготовка чисел, дат и времени к произнесению. По умолчанию `true`; для уже подготовленного текста можно указать `false`. |

Ответ сопоставляется одновременно по `clientId` и `deviceId`. Не подставляйте
вместо исходного ID устройства `media_player.*` или ID другой колонки: такой
ответ не попадёт в ожидающий диалог. `send_command` сам по себе не начинает
новый голосовой диалог и не проигрывает аудио — он возвращает результат
в уже ожидающий запрос.

## Что получает скрипт

Интеграция запускает выбранный `script.*` через `script.turn_on` и передаёт
одну переменную `dialog_payload`:

- `text` — исходная фраза пользователя;
- `client_id` и `device_id` — идентификаторы для возврата ответа;
- `command_id` и `continuation_id` — UUID основной команды и продолжения,
  если они определены;
- `direct_values` — распознанные значения прямых команд;
- `is_main_command` — признак главной команды среди совпавших в одной реплике.

Поле `context` в трассировке добавляет сам Home Assistant.

При источнике «Ответ из списка фраз» распознанная прямая команда выполняет
скрипт, использует основной ответ и завершает диалог (`end_session: true`),
даже если настроены продолжения. Например, «насыпь 2 грам еды» сразу передаёт
`count = 2`; вопрос о количестве нужен только для фразы без значения.
Для источника «Ответ из скрипта» сохраняются переходы по типу его результата.

## Событие активной команды (SSE)

Событие `ha_dialog_ui_active_command` передаёт данные в едином формате:

```json
{
  "event": "ha_dialog_ui_active_command",
  "data": {
    "client_id": "YOUR_CLIENT_ID",
    "command_data": [{
      "command_id": "5j78-5fs3-x8so-0e3e",
      "continuation_id": null,
      "text": "привет",
      "client_id": "YOUR_CLIENT_ID",
      "device_id": "YOUR_DEVICE_ID",
      "direct_values": [],
      "is_main_command": true
    }]
  }
}
```

`command_id` — UUID основной команды, `continuation_id` — UUID распознанного
продолжения или `null`. В условиях «Действий удалённых команд» указывайте эти
UUID: основная команда сравнивается с `command_id`, второстепенная — с
`continuation_id`. Для прямой команды используется её `command_id` внутри
`direct_values`; имя переменной (`name`) также поддерживается при сопоставлении.
`parent_type`, `children_type`, `children_direct_type` и `data.commands` больше
не публикуются: текст находится в `text`, значения — в `direct_values`.
Внутри прямого значения используются поля `command_id`, `name`, `value_type`,
`value` и при наличии вложенных совпадений `matched_codes`.

Если команда содержит привязку к HA-скрипту, дополнительно передаётся
`command_script` с `entity_id` и `run`. Такая привязка имеет приоритет над
поиском действия удалённой команды.

## HTTP API

API позволяет внешним приложениям отправлять текстовые команды в HA Dialog UI,
получать события и передавать ответы обратно. В настройках откройте «Подключения»,
включите «Включить API», задайте «Токен API команд» и сохраните изменения.
Это отдельная настройка от подключения к удалённому серверу: API принимает
входящие запросы, а подключение к серверу получает команды извне по SSE.

Во всех запросах нужен заголовок `Authorization: Bearer <токен API команд>`.
Используется токен из настроек интеграции, а не долгосрочный токен Home Assistant.
В примерах замените адрес Home Assistant, токен и идентификаторы своими значениями.

| Метод и адрес | Назначение |
| --- | --- |
| `POST /api/dialog/commands` | Обработать текстовую команду и получить результат диалога в JSON. |
| `GET /api/dialog/events` | Подписаться на события команд и ответов по SSE. |
| `POST /api/dialog/events` | Передать событие в интеграцию. |
| `GET/POST /api/dialog/event` | Синоним `/api/dialog/events` с тем же поведением. |

### Журнал API

При включённом API администратору доступен раздел «Логи». Он обновляется
каждые 3 секунды и показывает последние 200 записей: время, HTTP-метод, адрес
ручки, статус, длительность, подключения SSE и отправленные события.
Журнал хранится в памяти и очищается при перезапуске Home Assistant.
В раскрываемых блоках доступны JSON-тела запросов и ответов; у SSE — тело
каждого отправленного события. Заголовки авторизации и параметры URL не
сохраняются. Поля токенов, паролей и других секретов маскируются, настроенные
токены скрываются также внутри строк. Большие тела обрезаются для журнала
(ответ API при этом не меняется). При ошибке авторизации тело запроса не
читается; вместо некорректного JSON показывается отметка `invalid_json`.
Статус 499 в журнале означает закрытие соединения или отмену обработки,
а не отправленный сервером HTTP-ответ. Когда API выключен, новые записи
не собираются, а раздел журнала недоступен.

### Отправка команды

```sh
curl -X POST 'http://homeassistant.local:8123/api/dialog/commands' \
  -H 'Authorization: Bearer YOUR_API_COMMANDS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"text":"Включи свет","client_id":"YOUR_CLIENT_ID","device_id":"YOUR_DEVICE_ID","new_session":true}'
```

`text` — произнесённая или введённая фраза; `client_id` — идентификатор клиента;
`device_id` — идентификатор устройства, от которого пришла команда. Для колонки
Home Assistant это ID устройства из реестра HA, а не `entity_id` проигрывателя.
Если `client_id` не передан, используется значение из настроек интеграции.
Для продолжения диалога передавайте те же идентификаторы и `new_session: false`;
для новой команды — `true` (это значение по умолчанию).
Ответ имеет обёртку `{"response": ..., "version": "1.0"}`, где `response` содержит
результат обработки диалога. HTTP-запрос сам по себе не включает озвучку на колонке:
полученный ответ воспроизводит вызывающее приложение.

### Подписка на события

```sh
curl -N 'http://homeassistant.local:8123/api/dialog/events?clientId=YOUR_CLIENT_ID' \
  -H 'Authorization: Bearer YOUR_API_COMMANDS_TOKEN'
```

Соединение остаётся открытым. Сервер отправляет SSE-поля `event` и `data`,
где `data` — JSON с полями `event` и `data`. Параметр `clientId` (также допустим
`client_id`) ограничивает поток событиями одного клиента. Без него передаются
события всех клиентов. При отсутствии событий каждые 15 секунд приходит
комментарий `: keepalive`. После разрыва соединения клиенту нужно подключиться снова.

### Передача ответа скрипта

```sh
curl -X POST 'http://homeassistant.local:8123/api/dialog/events' \
  -H 'Authorization: Bearer YOUR_API_COMMANDS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"event":"dialog_message","data":{"client_id":"YOUR_CLIENT_ID","device_id":"YOUR_DEVICE_ID","actionType":"success","variables":{"reply":"Готово"}}}'
```

Для ответа используйте те же `client_id` и `device_id`, что пришли с командой.
`actionType` выбирает тип ответа, а `variables` передаёт значения для подстановок
в тексте, например `${reply}`. Это HTTP-вариант передачи события ответа;
внутри HA для этого удобнее сервис `ha_dialog_ui.send_command`.
Успешный приём события возвращает `{"accepted": true, "event": "dialog_message"}`.

При выключенном API, пустом или неверном токене сервер возвращает `401`.
Некорректный JSON или неподдерживаемое событие возвращают `400`.

## Удалённый сервер и интерфейс

«Подключаться к удалённому серверу» включает подключение к внешнему сервису
по SSE. Укажите адрес и токен в блоке «Подключения». Локальные разделы команд
скрываются; для пришедших команд используются «Действия удалённых команд».
Интеграция не поднимает внешний сервер, а подключается к существующему.

На мобильном слева в шапке — меню Home Assistant, справа — меню всех разделов
интеграции. Импорт и экспорт доступны только администратору.

## Разработка интерфейса

Исходники находятся в `ui`. Home Assistant использует собранные JS и CSS
из `custom_components/ha_dialog_ui/static`.

```bash
npm ci
npm run dev         # локальный Vite-сервер
npm run dev:ha      # сборка для HA с отслеживанием изменений
npm run build      # проверка TypeScript и production-сборка
npm run test:unit
CHROMIUM_PATH=/usr/bin/chromium npm run test:ui
```

Локальный dev-сервер по умолчанию доступен на `http://localhost:5173`.
